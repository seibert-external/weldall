Resources that act for people in other systems can now report those actions to Weldall's audit log. An app host, such as a registry that creates people's apps as repositories at the organisation's Git host and forwards their pushes there, reports with a machine client that holds the new machine-only system scope `weldall:app-host` and is allowed for the resource (`POST /api/app-host/v1/audit-events`). Each report is idempotent per `eventId`: a repeated identical report is answered as a duplicate, a different report under the same `eventId` with `409 event_id_conflict`. The person who acted is recorded as the actor, the machine client as the client and the resource as the subject; Weldall keeps no app records and stores the app id and repository as reported. The new audit event types are `git_repository.*` (created, registered, denied, failed), `app_owner.assigned` (an administrator assigned or changed an app's owner), `git_push.*`, `git_fetch.*`, `git_pull_request.*`, `git_credential.*`, `git_host.checked` and `app_confirmation.*`, each with a strict metadata schema, and they can be filtered under "Audit logs". Credentials (Git host tokens, git credentials, private keys, authorization headers and the like) are redacted from the free text of these events (reasons, ref, branch and template names) before it is stored, and now also from the server's logs; over-long free text is cut instead of refused. Identifiers and the metadata of all other audit events are stored as before. `POST /api/authorization/v1/check-scopes` also answers `weldall:login` for a machine client that holds `weldall:app-host` and has at least one enabled allowed resource, even when its resource does not support that scope, so such a resource can stop serving a person who may no longer use Weldall. A database migration adds the new audit event types; existing audit events are unchanged.

`weldall app` (singular) creates and publishes your own apps through your organisation's registry, without a Git account: `weldall app publish` creates the app on first use (`--name`, `--description`, `--share <permission>`, `--url`; repeating the same command after a stop continues with the same app), merges the repository's state, pushes one commit to a `weldall/publish-*` branch and opens or updates the pull request; `sync`, `status`, `list`, `confirm`, and for administrators `list --all`, `set-owner` and `checklist`. The CLI finds a registry only in Weldall's list (`registries` of `GET /api/me/apps`), never in a resource's own metadata, checks each entry against the resource's registration, sends git credentials only below a listed registry's git route, treats everything it reads back from the folder's `.git` as hostile (full object ids, bounded values, `--end-of-options` for git), renews an expired downstream token once, waits a short `Retry-After`, and explains every registry error in plain words. `weldall git-credential` is the credential helper git runs for that route. It never chooses one of several registries on its own: when Weldall lists more than one, a first publish, `checklist`, `list --all` and `set-owner` need `--registry` and the error lists each registry with its key, name, origin and whether you may use it; `confirm <id>` and `status --app <id>` stop when a registry cannot answer instead of using another that claims the id. Without a registry, every `weldall app` command says that publishing is not set up. Publish's lock and conflict state in `.git/weldall` are never written through a link or read from a pipe, and exactly one run takes over a stale lock. `weldall apps` (plural) accepts the new `registries` key and shows why Weldall refused a resource's apps API (`apps_api_refused`).

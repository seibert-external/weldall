Use machine authentication when one backend needs to call another without a person signing in. Each machine has its own client ID and key pair. It authenticates with OAuth 2.0 client credentials and RFC 7523 `private_key_jwt`, and Weldall returns a five-minute token for one resource.

## Register the calling service

The following example lets Expenses A read data from Expenses B:

1. Create the required scopes and register Expenses B under **Resources**.
2. Generate an ES256 P-256 key pair. Keep the private key with Expenses A.
3. Open **Machine clients**, select **Register machine**, and enter `expenses-a`, the public JWK, and a unique `kid`.
4. Under **Machine access**, select Expenses B under **Resources** and the required entries under **Scopes**.

Machine access is mainly controlled by two allowlists: the resources a machine may call and the scopes it may request. A token request must match both lists, and the target resource must support every requested scope. Registering a machine or resource by itself does not grant access.

## Request a token

The easiest setup is to provide the key pair through secret-backed environment variables. `loadEs256KeyPairFromEnv` validates them before the SDK creates the short-lived assertion and matching DPoP proof:

```ts
import { loadEs256KeyPairFromEnv, requestMachineToken } from "@weldall/sdk";

const key = await loadEs256KeyPairFromEnv({
  privateName: "MACHINE_SIGNING_PRIVATE_JWK",
  privateValue: process.env.MACHINE_SIGNING_PRIVATE_JWK!,
  publicName: "MACHINE_SIGNING_PUBLIC_JWK",
  publicValue: process.env.MACHINE_SIGNING_PUBLIC_JWK!,
});

const token = await requestMachineToken({
  issuer: "https://weldall.example.com",
  clientId: "expenses-a",
  resource: "https://expenses-b.example.com/api",
  scopes: ["expenses-b:read"],
  kid: process.env.MACHINE_SIGNING_KID!,
  key,
});
```

Configure these environment variables through your deployment platform's secret management. A KMS, Vault, or another credential provider is a good fit when you already use one. Never put the private JWK in Weldall, application manifests, source control, or logs.

The response contains a DPoP-bound access token and no refresh token. Request a new token when the current one expires.

## Check a user's current scopes

A backend that must re-evaluate a persistent local credential can request the machine-only `weldall:subject-scopes-check` scope for the Weldall API. Assign that system scope and the backend's own resource to its machine client. Weldall only permits checks for scopes supported by one of the machine's allowed resources. A machine client that also holds `weldall:app-host` (see [below](#report-audit-events-for-a-resource)) and has at least one enabled allowed resource may also check `weldall:login` when its resource does not support it, so a resource that acts for people with its own credentials can stop serving a person who may no longer use Weldall. Any other machine checks `weldall:login` only when one of its allowed resources supports it.

Use the opaque `sub` captured from a previously verified Weldall user token, never an email address:

```ts
import { createDpopProof, requestMachineToken } from "@weldall/sdk";

const issuer = "https://weldall.example.com";
const token = await requestMachineToken({
  issuer,
  clientId: "randomapp",
  resource: `${issuer}/api`,
  scopes: ["weldall:subject-scopes-check"],
  kid: process.env.MACHINE_SIGNING_KID!,
  key,
});
const endpoint = `${issuer}/api/authorization/v1/check-scopes`;
const proof = await createDpopProof({
  ...key,
  method: "POST",
  url: endpoint,
  accessToken: token.accessToken,
});
const response = await fetch(endpoint, {
  method: "POST",
  headers: {
    authorization: `DPoP ${token.accessToken}`,
    dpop: proof,
    "content-type": "application/json",
  },
  body: JSON.stringify({ subject, scopes: ["randomapp:mint-key"] }),
});
```

A successful response contains sorted `granted` and `missing` arrays plus `evaluatedAt`. Responses are marked `no-store`; a caller may apply its own short cache. Weldall returns `503 temporarily_unavailable` rather than reporting an authoritative missing scope when a relevant group provider cannot be evaluated.

## Report audit events for a resource

Some resources act on people's behalf in other systems. An app host, for example a registry that creates apps as repositories at your organisation's Git host and forwards people's pushes there, does so with its own long-lived Git host credential. So that Weldall's audit log still shows who did what, such a resource reports these actions to Weldall with its machine client.

Assign the machine-only system scope `weldall:app-host` and the resource itself to the resource's machine client. Request the token for the Weldall API (`${issuer}/api`) with the scope `weldall:app-host` and send each event to `POST /api/app-host/v1/audit-events`, signed with a fresh DPoP proof as in the check above. Every report names the resource identifier of the resource it is about; Weldall accepts it only when the machine client is allowed for that resource and the resource is enabled, and answers `403 invalid_target` otherwise.

```json
{
  "resource": "https://registry.example.com/api",
  "eventId": "0f3c4f0e-6a1b-4c1e-9d55-6b2f3c0d9a10",
  "eventType": "git_push.forwarded",
  "subject": "user-1",
  "appId": "app_0123456789abcdef0123",
  "repository": { "owner": "acme-apps", "name": "app-expenses" },
  "details": {
    "refUpdates": [
      {
        "ref": "refs/heads/weldall/publish-1",
        "oldCommit": "0000000000000000000000000000000000000000",
        "newCommit": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
      }
    ],
    "refUpdateCount": 1,
    "credentialId": "c2f6b1d0-3e4a-4b7c-9f21-8d5e6a7b9c01"
  }
}
```

- `subject` is the Weldall user ID (`sub`) of the person who acted, never an email address. An unknown or unverified person is `404 unknown_subject`. Rejections may have `subject: null`; the machine client is then recorded as the actor.
- `appId` is the resource's own ID for the app; Weldall keeps no app records and stores it as reported, together with the repository. The resource decides who may act on an app.
- The event types are `git_repository.created`, `git_repository.registered` (an administrator registered an existing repository as someone's app), `app_owner.assigned` (an administrator assigned or changed an app's owner), `git_push.forwarded` (before the push is forwarded), `git_push.completed`, `git_fetch.completed`, `git_pull_request.opened`, `git_credential.issued`, `git_host.checked` (the set-up checklist ran) and `app_confirmation.succeeded`, plus `.denied` and `.failed` rejections of repositories, pushes, fetches, pull requests and git credentials and `app_confirmation.denied`. A rejection carries a `reason` and optionally a `reasonCode`. Each event type has its own fixed `details`; a body that does not match is `400 invalid_request`.
- `eventId` (16 to 128 characters of letters, digits, `.`, `_`, `:` and `-`) is chosen by the resource and reused on every retry of the same report. A new entry is answered with `201`, a repeated identical report with `200` and `duplicate: true`, and a different report under an `eventId` already used with `409 event_id_conflict`. Only a `2xx` answer with `accepted: true` means the entry is stored, so a resource that must not act without an audit entry (such as forwarding a push) acts only after that answer.

A report body may be at most 64,000 bytes, and each free text in it (a `reason`, a ref, branch or template name) at most 8,000 characters. Weldall redacts credentials from free text, replaces control characters and invalid Unicode in it, and cuts it before storing it: reasons to 500 characters, ref and branch names to 255 and template names to 100, ending in `…[truncated]`. A long name therefore never makes a report fail. IDs, repository names and commit IDs are checked against their format instead and stored unchanged. The entries appear under **Audit logs** with the resource as their subject and the machine client as their client.

## Protect the receiving service

Expenses B uses the same `initWeldall` setup as an API that serves employees:

```ts
import { inMemory } from "@weldall/sdk";
import { initWeldall, type WeldallVariables } from "@weldall/sdk/hono";
import { Hono } from "hono";

const weldall = initWeldall("https://weldall.example.com", {
  resource: "https://expenses-b.example.com/api",
  publicOrigin: "https://expenses-b.example.com",
  clientId: "expenses-b",
  supportedScopes: ["expenses-b:read"],
  signingKey: loadExpensesBSigningKey(),
  replayStore: inMemory(),
});

const app = new Hono<{ Variables: WeldallVariables }>();
app.get("/api/expenses", weldall.protect({ scopes: ["expenses-b:read"] }), (context) => {
  const auth = weldall.getAuth(context);
  return context.json({
    subject: auth.subject,
    requestedBy: auth.identity.type === "machine" ? auth.identity.clientId : auth.identity.email,
    identityType: auth.identityType,
    ...(auth.identityType === "user" ? { email: auth.email } : {}),
    expenses: [],
  });
});
```

`protect` checks the token and required scopes before the handler runs. `getAuth` tells the handler whether the caller is a user or a machine. Most routes only need their scope policy; check `auth.identity.type` when the response or business logic needs caller details such as an email address or machine client ID.

Machine tokens never contain a user's email address and cannot impersonate a user.

## Rotate or revoke a key

Register the new public key before deploying its private counterpart. Keep both keys active during the rollout, switch the machine to the new `kid`, and then revoke the old key.

You can also deactivate the machine client or remove entries from either access allowlist. These changes stop new token issuance immediately. Tokens already issued expire within five minutes.

Machine registration, token issuance, and rejected requests appear under **Audit logs**. Assertions, tokens, proofs, and key material are not written to the audit log.

## Security flow

The complete request flow has two verification points: Weldall checks the machine, its key, and its access policy before issuing a short-lived token; the receiving API then verifies that token and the fresh DPoP proof attached to the request.

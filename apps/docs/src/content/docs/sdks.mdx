Weldall publishes two npm packages. The CLI runs on an employee's device. The SDK runs inside a connected service.

## `@weldall/cli`

[`@weldall/cli`](https://www.npmjs.com/package/@weldall/cli) installs the `weldall` command. Node.js 22.15 or newer is required.

### npm (recommended)

```sh
npm install --global @weldall/cli@latest
weldall --version
```

### Experimental standalone binaries

Standalone binaries require no Node.js, npm, or Bun. Initial targets are Linux x64, Windows x64, and macOS ARM64/x64. They are currently unsigned. Download the appropriate asset from [GitHub Releases](https://github.com/seibert-external/weldall/releases).

```sh
# macOS, after downloading the trusted binary
xattr -d com.apple.quarantine ./weldall
chmod +x ./weldall

# Linux
chmod +x ./weldall
```

Windows PowerShell: `Unblock-File .\weldall.exe`.

## `@weldall/sdk`

[`@weldall/sdk`](https://www.npmjs.com/package/@weldall/sdk) validates requests before a service reads data or makes changes. It provides a Fetch API and adapters for Hono, Next.js, and Astro.

```sh
pnpm add @weldall/sdk
```

Create one Weldall instance when the service starts:

```ts
import { initWeldall } from "@weldall/sdk";

const weldall = initWeldall("https://weldall.example.com", {
  resource: "https://contracts.example.com/api",
  publicOrigin: "https://contracts.example.com",
  clientId: "weldall-cli-at-contracts",
  supportedScopes: ["contracts:read", "contracts:update"],
  signingKey,
  replayStore,
});
```

In a Fetch handler, `weldall.verify(request, { scopes: [...] })` checks the request before business logic runs. Framework adapters provide middleware or handler wrappers:

- `@weldall/sdk/hono`
- `@weldall/sdk/next`
- `@weldall/sdk/astro`

The SDK requires Node.js 22.15 or newer. Next.js routes must use the Node.js runtime.

## Publish skills from a service

A resource can publish its own agent instructions. Add a `skills` provider to the same SDK configuration:

```ts
const weldall = initWeldall("https://weldall.example.com", {
  resource: "https://contracts.example.com/api",
  publicOrigin: "https://contracts.example.com",
  clientId: "weldall-cli-at-contracts",
  supportedScopes: ["contracts:read"],
  signingKey,
  replayStore,
  skills: {
    items: [
      {
        id: "list",
        title: "List contracts",
        requiredScopes: ["contracts:read"],
        visibility: "HIDDEN_IF_UNALLOWED",
        content:
          "# List contracts\n\nRun `weldall request --scope contracts:read https://contracts.example.com/api/contracts`.",
      },
    ],
  },
});
```

Skill IDs are local to the resource. If the registered resource key is `contracts`, Weldall exposes this skill as `contracts.list`.

Use `skills.load` instead of `skills.items` when the catalog comes from a database or another local source:

```ts
skills: {
  load: async () => loadPublishedSkills(),
}
```

The provider receives no employee identity. It must return the same catalog for every caller.

`DEFAULT` keeps a skill visible and reports missing scopes. `HIDDEN_IF_UNALLOWED` hides it unless the employee has every required scope. Visibility controls discovery, not authorization: the API route still needs its own protection policy, and skill instructions never grant access. Required scopes, including protected system scopes, must already exist in Weldall; unknown scopes are withheld from users and shown as warnings to administrators.

The Hono adapter mounts the catalog route through `weldall.registerRoutes(app)`. Fetch, Next.js, and Astro integrations must expose `weldall.handlers.skills` at `/.well-known/weldall-skills` alongside the OAuth metadata, token, and JWKS handlers.

See [How to: Integrate a service](../service-configuration/) for a complete Hono setup. [Security](../oauth-security/) covers keys, replay protection, and the protocol boundary.

Weldall veröffentlicht zwei npm-Pakete. Die CLI läuft auf dem Gerät eines Mitarbeiters. Das SDK läuft im angebundenen Service.

## `@weldall/cli`

[`@weldall/cli`](https://www.npmjs.com/package/@weldall/cli) installiert den Befehl `weldall`. Mitarbeitende melden sich damit an. Agenten entdecken Skills und senden freigegebene Requests an Unternehmensservices.

Wähle entweder das JavaScript-npm-Paket (Node.js 22.15 oder neuer erforderlich) oder eine eigenständige, selbstenthaltene ausführbare Datei (kein Node.js, npm, Bun oder `node_modules` erforderlich). Beide enthalten die vollständige CLI.

```sh
npm install --global @weldall/cli@latest
```

| System         | Unterstützte Version               | Architektur           | npm | Standalone-Archiv     |
| -------------- | ---------------------------------- | --------------------- | --- | --------------------- |
| Ubuntu Linux   | Aktuell unterstützte Ubuntu-LTS    | x64                   | Ja  | `linux-x64.tar.gz`    |
| Windows-Client | Windows 10 Version 1809 oder neuer | x64                   | Ja  | `windows-x64.zip`     |
| Windows Server | Windows Server 2019 oder neuer     | x64                   | Ja  | `windows-x64.zip`     |
| macOS          | Aktuell unterstützte Versionen     | ARM64 / Apple Silicon | Ja  | `darwin-arm64.tar.gz` |
| macOS          | Aktuell unterstützte Versionen     | Intel x64             | Ja  | `darwin-x64.tar.gz`   |

Die Windows-Untergrenze gilt für beide Distributionen und folgt der strengeren gemeinsamen Voraussetzung von Node.js 22 und der eingebetteten Bun-1.3-Laufzeit. Standalone-Dateien sind derzeit **nicht signiert**. Sie sind weder von Apple notarisiert noch mit Authenticode signiert; Installer, Homebrew und WinGet werden nicht angeboten. Lade sie nur aus dem GitHub Release mit dem Tag `@weldall/cli@X.Y.Z` und prüfe `SHA256SUMS`, bevor du die ausführbare Datei ersetzt.

POSIX-Beispiel (wähle `linux-x64`, `darwin-arm64` oder `darwin-x64`):

```sh
VERSION=1.2.3
TARGET=linux-x64
ARCHIVE="weldall-v${VERSION}-${TARGET}.tar.gz"
BASE="https://github.com/seibert-external/weldall/releases/download/%40weldall%2Fcli%40${VERSION}"
curl -fLO "$BASE/$ARCHIVE" && curl -fLO "$BASE/SHA256SUMS"
EXPECTED="$(awk -v file="$ARCHIVE" '$2 == file { print $1 }' SHA256SUMS)"
if command -v shasum >/dev/null 2>&1; then
  ACTUAL="$(shasum -a 256 "$ARCHIVE" | awk '{print $1}')"
else
  ACTUAL="$(sha256sum "$ARCHIVE" | awk '{print $1}')"
fi
test -n "$EXPECTED" && test "$ACTUAL" = "$EXPECTED"
mkdir -p "$HOME/.local/bin"
tar -xzf "$ARCHIVE"
install -m 0755 weldall "$HOME/.local/bin/weldall"
```

PowerShell-Beispiel:

```powershell
$Version = "1.2.3"
$Archive = "weldall-v$Version-windows-x64.zip"
$Tag = [uri]::EscapeDataString("@weldall/cli@$Version")
$Base = "https://github.com/seibert-external/weldall/releases/download/$Tag"
Invoke-WebRequest "$Base/$Archive" -OutFile $Archive
Invoke-WebRequest "$Base/SHA256SUMS" -OutFile SHA256SUMS
$Expected = ((Select-String SHA256SUMS -Pattern "^[0-9a-f]{64}  $([regex]::Escape($Archive))$").Line -split "  ")[0]
if ((Get-FileHash $Archive -Algorithm SHA256).Hash.ToLowerInvariant() -ne $Expected) { throw "Prüfsummenfehler" }
Expand-Archive $Archive .\weldall-release -Force
$Bin = "$HOME\bin"
New-Item -ItemType Directory -Force $Bin | Out-Null
Copy-Item .\weldall-release\weldall.exe "$Bin\weldall.exe" -Force
$UserPath = [Environment]::GetEnvironmentVariable("Path", "User")
if (($UserPath -split ";") -notcontains $Bin) {
  [Environment]::SetEnvironmentVariable("Path", "$Bin;$UserPath", "User")
}
$env:Path = "$Bin;$env:Path"
```

Die Änderung des Benutzer-`Path` gilt dauerhaft für künftige Windows-Sitzungen. Die Zuweisung an `$env:Path` wirkt nur im aktuellen PowerShell-Prozess; öffne bei Bedarf ein neues Terminal.

Aktualisiere npm-Installationen mit `npm install --global @weldall/cli@latest`. Für ein Standalone-Upgrade prüfst du das neue Archiv und ersetzt anschließend die ausführbare Datei.

Die nicht geheime Issuer-Einstellung liegt unter Linux in `~/.weldall/config.json`, unter Windows in `%USERPROFILE%\.weldall\config.json` und unter macOS weiterhin im Defaults-Domain/Key `dev.seibert.weldall-cli/Issuer`. Ein temporäres Override setzt du in POSIX-Shells mit `export WELDALL_ISSUER=https://weldall.example.com` und in PowerShell mit `$env:WELDALL_ISSUER = "https://weldall.example.com"`.

Zugangsdaten und DPoP-Schlüssel liegen im Windows Credential Manager, macOS-Schlüsselbund oder Linux Secret Service mit Kernel-keyutils-Fallback – niemals in der Issuer-Datei. Unter Ubuntu Desktop muss der Login-Schlüsselbund entsperrt sein. Headless-Linux-Sitzungen benötigen einen Benutzer-D-Bus mit entsperrtem Secret Service (etwa `gnome-keyring-daemon`) oder eine nutzbare Kernel-Keyring/keyutils-Umgebung. Andernfalls schlagen Sitzungsbefehle mit dem sichtbaren Backend-Fehler fehl, statt Klartextzugangsdaten zu speichern.

## `@weldall/sdk`

[`@weldall/sdk`](https://www.npmjs.com/package/@weldall/sdk) prüft Requests, bevor ein Service Daten liest oder Änderungen ausführt. Es stellt eine Fetch-API und Adapter für Hono, Next.js und Astro bereit.

```sh
pnpm add @weldall/sdk
```

Erzeuge beim Start des Services eine Weldall-Instanz:

```ts
import { initWeldall } from "@weldall/sdk";

const weldall = initWeldall("https://weldall.example.com", {
  resource: "https://contracts.example.com/api",
  publicOrigin: "https://contracts.example.com",
  clientId: "weldall-cli-at-contracts",
  supportedScopes: ["contracts:read", "contracts:update"],
  signingKey,
  replayStore,
});
```

In einem Fetch-Handler prüft `weldall.verify(request, { scopes: [...] })` den Request vor der Geschäftslogik. Die Framework-Adapter stellen dafür Middleware oder Handler-Wrapper bereit:

- `@weldall/sdk/hono`
- `@weldall/sdk/next`
- `@weldall/sdk/astro`

Das SDK benötigt Node.js 22.15 oder neuer. Next.js-Routen müssen die Node.js-Runtime verwenden.

## Skills aus einem Service veröffentlichen

Eine Resource kann ihre Agentenanweisungen selbst veröffentlichen. Ergänze dazu einen `skills`-Provider in derselben SDK-Konfiguration:

```ts
const weldall = initWeldall("https://weldall.example.com", {
  resource: "https://contracts.example.com/api",
  publicOrigin: "https://contracts.example.com",
  clientId: "weldall-cli-at-contracts",
  supportedScopes: ["contracts:read"],
  signingKey,
  replayStore,
  skills: {
    items: [
      {
        id: "list",
        title: "Verträge auflisten",
        requiredScopes: ["contracts:read"],
        visibility: "HIDDEN_IF_UNALLOWED",
        content:
          "# Verträge auflisten\n\nFühre `weldall request --scope contracts:read https://contracts.example.com/api/contracts` aus.",
      },
    ],
  },
});
```

Skill-IDs gelten lokal für die Resource. Hat die registrierte Resource den Key `contracts`, stellt Weldall diesen Skill als `contracts.list` bereit.

Wenn der Katalog aus einer Datenbank oder einer anderen lokalen Quelle kommt, verwende `skills.load` statt `skills.items`:

```ts
skills: {
  load: async () => loadPublishedSkills(),
}
```

Der Provider erhält keine Identität eines Mitarbeiters. Er muss für alle Aufrufer denselben Katalog liefern.

`DEFAULT` lässt einen Skill sichtbar und weist auf fehlende Scopes hin. `HIDDEN_IF_UNALLOWED` blendet ihn aus, solange dem Mitarbeiter ein benötigter Scope fehlt. Die Sichtbarkeit steuert nur die Discovery, nicht die Autorisierung: Die API-Route benötigt weiterhin eine eigene Schutzregel, und Skill-Anweisungen gewähren keinen Zugriff. Die Scopes müssen bereits in Weldall existieren; das gilt auch für geschützte System-Scopes. Unbekannte Scopes werden Nutzern nicht angezeigt und erscheinen als Warnung für Administratoren.

Der Hono-Adapter registriert die Katalogroute mit `weldall.registerRoutes(app)`. Bei Fetch, Next.js und Astro muss `weldall.handlers.skills` unter `/.well-known/weldall-skills` erreichbar sein – neben den Handlern für OAuth-Metadaten, Token und JWKS.

Eine vollständige Hono-Einrichtung zeigt [How to: Service integrieren](../service-configuration/). Hintergründe zu Schlüsseln, Replay-Schutz und Protokollen stehen unter [Sicherheit](../oauth-security/).

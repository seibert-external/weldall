This guide deploys Weldall as a Cloud Run service with one instance, stores its data in Cloud SQL for PostgreSQL and its secrets in Secret Manager, and deploys the discovery proxy as a second, independent Cloud Run service. It ends with a backup, an upgrade and a rollback, so you know the procedure before you need it.

[Docker images](../docker/) explains the images, tags and start-up behavior this guide relies on.

## Before you start

- A Google Cloud project with billing enabled, and the Owner role in it.
- [Cloud Shell](https://cloud.google.com/shell). It has `gcloud`, `node` and `jq` preinstalled; every command below runs there.
- The Weldall version you want to run, for example `0.1.1`. The available versions are on the [GitHub releases page](https://github.com/seibert-external/weldall/releases).
- Access to your identity provider to create an OIDC client, see [How to: Run the installer](../installer/).

Set these variables once per Cloud Shell session:

```sh
PROJECT=your-project-id
PROJECT_NUMBER=$(gcloud projects describe "$PROJECT" --format="value(projectNumber)")
REGION=europe-west3
WELDALL_VERSION=0.1.1
PROXY_VERSION=0.1.1
gcloud config set project "$PROJECT"
```

The Cloud SQL instance costs money for as long as it exists, whether Weldall is used or not. The Cloud Run services cost almost nothing while idle.

## 1. Enable the services

```sh
gcloud services enable run.googleapis.com sqladmin.googleapis.com \
  secretmanager.googleapis.com iam.googleapis.com
```

## 2. Create the database

```sh
gcloud sql instances create weldall-db \
  --region "$REGION" \
  --database-version POSTGRES_16 \
  --edition ENTERPRISE \
  --tier db-f1-micro \
  --storage-size 10 --storage-type SSD \
  --backup-start-time 03:00 \
  --availability-type zonal

gcloud sql databases create weldall --instance weldall-db
```

- Creating the instance takes about 15 minutes.
- `db-f1-micro` is the smallest machine type and suited for a test. For production, choose a dedicated-core type such as `db-custom-1-3840`.
- `--edition ENTERPRISE` is required for the small machine types; PostgreSQL 16 otherwise defaults to Enterprise Plus.
- `--backup-start-time` enables daily automatic backups. You still take an on-demand backup before every upgrade, see [step 9](#9-upgrade-weldall).

## 3. Create the database user

Weldall applies its migrations on every start, so its database user must be allowed to change the schema. A user created with `gcloud sql users create` is a member of `cloudsqlsuperuser` and can create and alter tables in the `public` schema of `weldall`.

The password goes directly into the connection URL in Secret Manager and is not stored anywhere else:

```sh
CONN="${PROJECT}:${REGION}:weldall-db"
pw=$(node -e 'process.stdout.write(require("node:crypto").randomBytes(24).toString("base64url"))')
gcloud sql users create weldall --instance weldall-db --password "$pw"
printf 'postgresql://weldall:%s@localhost/weldall?host=/cloudsql/%s' "$pw" "$CONN" \
  | gcloud secrets create weldall-postgres-url \
      --replication-policy user-managed --locations "$REGION" --data-file=-
unset pw
```

Cloud Run connects to Cloud SQL through a Unix socket under `/cloudsql/`. The host in the URL stays `localhost`; the socket path is the `host` parameter. The instance needs no authorized networks.

:::note
In `zsh`, write `${PROJECT}:${REGION}` with braces. Without them, `zsh` reads the colon as a modifier and builds a wrong instance name.
:::

## 4. Create the service accounts

Each service runs under its own account with only the permissions it needs. The proxy needs none.

```sh
gcloud iam service-accounts create weldall-run --display-name "Weldall on Cloud Run"
gcloud iam service-accounts create weldall-proxy-run --display-name "Weldall discovery proxy on Cloud Run"

gcloud projects add-iam-policy-binding "$PROJECT" \
  --member "serviceAccount:weldall-run@${PROJECT}.iam.gserviceaccount.com" \
  --role roles/cloudsql.client --condition=None
```

## 5. Store the secrets

The command generates the secrets, writes each one directly to Secret Manager without printing it, and lets only `weldall-run` read them:

```sh
tmp=$(mktemp); chmod 600 "$tmp"
node -e '
const { generateKeyPairSync, randomBytes, randomUUID } = require("node:crypto");
const { privateKey, publicKey } = generateKeyPairSync("ec", { namedCurve: "P-256" });
process.stdout.write(JSON.stringify({
  "weldall-better-auth-secret": randomBytes(32).toString("base64url"),
  "weldall-setup-token": randomBytes(32).toString("base64url"),
  "weldall-credential-encryption-key": randomBytes(32).toString("base64"),
  "weldall-signing-private-jwk": JSON.stringify(privateKey.export({ format: "jwk" })),
  "weldall-signing-public-jwk": JSON.stringify(publicKey.export({ format: "jwk" })),
  "weldall-signing-kid": randomUUID(),
}));' > "$tmp"

for name in weldall-better-auth-secret weldall-setup-token weldall-credential-encryption-key \
            weldall-signing-private-jwk weldall-signing-public-jwk weldall-signing-kid; do
  jq -j --arg k "$name" '.[$k]' "$tmp" | gcloud secrets create "$name" \
    --replication-policy user-managed --locations "$REGION" --data-file=-
done
rm -f "$tmp"

for name in weldall-postgres-url weldall-better-auth-secret weldall-setup-token \
            weldall-credential-encryption-key weldall-signing-private-jwk \
            weldall-signing-public-jwk weldall-signing-kid; do
  gcloud secrets add-iam-policy-binding "$name" \
    --member "serviceAccount:weldall-run@${PROJECT}.iam.gserviceaccount.com" \
    --role roles/secretmanager.secretAccessor
done
```

Keep these secrets for the life of the installation. [Docker images](../docker/#generate-the-secrets) explains why.

## 6. Deploy Weldall

The URL of a Cloud Run service is known before the first deployment: `https://SERVICE-PROJECT_NUMBER.REGION.run.app`. Weldall needs it as `WELDALL_ISSUER` from the first start, because the callback URL you register at your identity provider is built from it.

```sh
WELDALL_URL="https://weldall-${PROJECT_NUMBER}.${REGION}.run.app"

gcloud run deploy weldall --region "$REGION" \
  --image "docker.io/seibertmediagmbh/weldall:${WELDALL_VERSION}" \
  --service-account "weldall-run@${PROJECT}.iam.gserviceaccount.com" \
  --port 3000 --cpu 1 --memory 1Gi \
  --min-instances 0 --max-instances 1 \
  --add-cloudsql-instances "$CONN" \
  --set-env-vars "WELDALL_ISSUER=${WELDALL_URL},WELDALL_DEPLOYMENT_MODE=production,WELDALL_CREDENTIAL_ENCRYPTION_KEY_VERSION=1" \
  --set-secrets "POSTGRES_URL=weldall-postgres-url:latest,BETTER_AUTH_SECRET=weldall-better-auth-secret:latest,WELDALL_SETUP_TOKEN=weldall-setup-token:latest,WELDALL_CREDENTIAL_ENCRYPTION_KEY=weldall-credential-encryption-key:latest,WELDALL_SIGNING_PRIVATE_JWK=weldall-signing-private-jwk:latest,WELDALL_SIGNING_PUBLIC_JWK=weldall-signing-public-jwk:latest,WELDALL_SIGNING_KID=weldall-signing-kid:latest" \
  --startup-probe "httpGet.path=/.well-known/openid-configuration,httpGet.port=3000,periodSeconds=5,timeoutSeconds=3,failureThreshold=48" \
  --liveness-probe "httpGet.path=/.well-known/openid-configuration,httpGet.port=3000,periodSeconds=30,timeoutSeconds=5,failureThreshold=3" \
  --allow-unauthenticated
```

- `--max-instances 1` keeps Weldall to one instance. [Docker images](../docker/#why-exactly-one-weldall-container) explains why, and [Availability](#availability-with-one-instance) what it means on Cloud Run.
- Cloud Run ignores the Docker `HEALTHCHECK`. The startup probe gives the first start four minutes for the migrations; the liveness probe restarts a hanging instance.
- `--allow-unauthenticated` makes Weldall reachable for browsers, the CLI and resource servers. Cloud Run provides the HTTPS certificate for the `run.app` URL. The installer stays closed to anyone without the setup token.
- `--min-instances 0` lets Cloud Run stop the instance when idle. The first request afterwards waits for a cold start of a few seconds. `--min-instances 1` avoids that and is billed continuously.

## 7. Verify Weldall and run the installer

```sh
curl -s "$WELDALL_URL/.well-known/openid-configuration" | jq -r .issuer   # prints $WELDALL_URL
curl -s "$WELDALL_URL/api/me/skills"                                    # 401 invalid_token

gcloud logging read \
  'resource.type="cloud_run_revision" AND resource.labels.service_name="weldall"' \
  --order=asc --limit 200 --format="value(textPayload,jsonPayload.message)" \
  | grep -E "migrations found|Applying migration|successfully applied|No pending|Deployment initialization|server initialized"
```

On the first start, the log shows every migration being applied, `All migrations have been successfully applied.`, then `Deployment initialization completed`, then `Weldall server initialized`.

Open `$WELDALL_URL` and follow [How to: Run the installer](../installer/). Copy the setup token to the clipboard without printing it, for example in a local terminal on macOS:

```sh
gcloud secrets versions access latest --secret weldall-setup-token --project "$PROJECT" | pbcopy
```

:::note[Google as identity provider]
If you create the OAuth client in Google Cloud, the audience type **Internal** admits only accounts of the Google organization that owns the project. If your employee accounts belong to a different organization, Google rejects the login with `Error 403: org_internal`. Use **External** and publish the app, or, for a test, keep it in **Testing** and add the accounts under **Test users**.

Run the installer's test login with **Allowed email domains** left empty first. Add the domain restriction after the test passed and test again; the result page does not name the reason when a test login fails.
:::

## 8. Deploy the discovery proxy

Skip this step if all your resource servers can reach `$WELDALL_URL` directly.

```sh
gcloud run deploy weldall-discovery-proxy --region "$REGION" \
  --image "docker.io/seibertmediagmbh/discovery-proxy:${PROXY_VERSION}" \
  --service-account "weldall-proxy-run@${PROJECT}.iam.gserviceaccount.com" \
  --port 8080 --cpu 1 --memory 256Mi \
  --min-instances 0 --max-instances 3 \
  --set-env-vars "WELDALL_UPSTREAM=${WELDALL_URL}" \
  --startup-probe "tcpSocket.port=8080,periodSeconds=2,timeoutSeconds=1,failureThreshold=15" \
  --allow-unauthenticated
```

Verify that the proxy forwards both documents unchanged and blocks everything else:

```sh
PROXY_URL="https://weldall-discovery-proxy-${PROJECT_NUMBER}.${REGION}.run.app"
cmp <(curl -s "$WELDALL_URL/.well-known/oauth-authorization-server") \
    <(curl -s "$PROXY_URL/.well-known/oauth-authorization-server") && echo identical
cmp <(curl -s "$WELDALL_URL/api/oauth/jwks") <(curl -s "$PROXY_URL/api/oauth/jwks") && echo identical
curl -s -o /dev/null -w "%{http_code}\n" "$PROXY_URL/.well-known/openid-configuration"   # 404
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$PROXY_URL/api/oauth/jwks"             # 405
```

Resource servers use `$PROXY_URL` as `discoveryProxyOrigin` and keep `$WELDALL_URL` as the issuer, see [Discovery proxy](../discovery-proxy/).

## 9. Upgrade Weldall

Take a backup directly before the upgrade and note its ID:

```sh
NEW_VERSION=0.1.2   # the version you upgrade to
gcloud sql backups create --instance weldall-db --description "before Weldall ${NEW_VERSION}"
gcloud sql backups list --instance weldall-db --limit 3
```

Deploy the new version. Only the image changes; Cloud Run keeps every other setting of the previous revision:

```sh
gcloud run deploy weldall --region "$REGION" \
  --image "docker.io/seibertmediagmbh/weldall:${NEW_VERSION}"
```

The log of the new revision shows only the new migrations, then the initialization and the server start. Run the checks from [step 7](#7-verify-weldall-and-run-the-installer) again.

## 10. Roll Weldall back

Starting the previous image alone is not enough. The older version starts without a warning and reports `No pending migrations to apply.`, while the database keeps the schema of the newer version. [Docker images](../docker/#upgrades-and-rollbacks) explains the consequences.

Restore the backup from step 9, then start the previous image:

```sh
gcloud sql backups restore BACKUP_ID --restore-instance weldall-db --backup-instance weldall-db
gcloud run deploy weldall --region "$REGION" \
  --image "docker.io/seibertmediagmbh/weldall:${WELDALL_VERSION}"
```

- The restore replaces the whole instance with the state of the backup. Logins, administration changes and audit records written after the backup are lost.
- The database is unavailable during the restore, which takes several minutes. Plan a maintenance window.

## 11. Upgrade and roll back the proxy

The proxy stores nothing and is independent of Weldall. Upgrade it with a new image, and roll it back by sending the traffic to the previous revision:

```sh
NEW_PROXY_VERSION=0.1.2   # the version you upgrade to
gcloud run deploy weldall-discovery-proxy --region "$REGION" \
  --image "docker.io/seibertmediagmbh/discovery-proxy:${NEW_PROXY_VERSION}"

gcloud run revisions list --service weldall-discovery-proxy --region "$REGION"
gcloud run services update-traffic weldall-discovery-proxy --region "$REGION" \
  --to-revisions PREVIOUS_REVISION=100
```

After `--to-revisions`, the traffic stays pinned to that revision, and later deployments receive none. Undo the pin before the next upgrade:

```sh
gcloud run services update-traffic weldall-discovery-proxy --region "$REGION" --to-latest
```

Do not roll back Weldall this way: it would reactivate an old revision without restoring the database.

## Availability with one instance

- `--max-instances` applies per revision. During a deployment, Cloud Run starts the new revision while the old one still serves requests, so two Weldall processes run for a short time. The window closes when the traffic has switched.
- While the only instance starts, Weldall does not answer. This happens during upgrades, after idle periods with `--min-instances 0`, and when Cloud Run replaces an instance.
- Cloud SQL maintenance and restores make the database temporarily unavailable. Weldall then fails requests that need the database.
- Weldall has no high-availability setup. Plan upgrades and restores for times with little use.

## Remove the test installation

A test setup keeps costing money until the Cloud SQL instance is deleted:

```sh
gcloud run services delete weldall weldall-discovery-proxy --region "$REGION"
gcloud sql instances delete weldall-db
for name in weldall-postgres-url weldall-better-auth-secret weldall-setup-token \
            weldall-credential-encryption-key weldall-signing-private-jwk \
            weldall-signing-public-jwk weldall-signing-kid; do
  gcloud secrets delete "$name" --quiet
done
gcloud iam service-accounts delete "weldall-run@${PROJECT}.iam.gserviceaccount.com" --quiet
gcloud iam service-accounts delete "weldall-proxy-run@${PROJECT}.iam.gserviceaccount.com" --quiet
```

By default, deleting the instance also deletes its automatic and on-demand backups.

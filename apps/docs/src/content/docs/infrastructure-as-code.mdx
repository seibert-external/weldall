All administrative features of the Weldall server can be managed through its user interface. The most important building blocks – scopes, resources, machine clients, administrator-managed skills, and assignments – can also be described in YAML files. This turns the configuration into infrastructure as code (IaC).

<Aside type="tip" title="Why IaC?">
  Every change remains traceable in a version-controlled Git repository. Pull requests provide a
  place to discuss and approve changes, while comments in the YAML document why a particular
  permission exists.
</Aside>

<Aside title="Atomic changes">
  Weldall groups the YAML files into a workspace and applies the desired state atomically: Either
  every planned change is applied or none of them are.
</Aside>

Even when using IaC, people with the appropriate permissions can continue to use the user interface to make changes or create new scopes, resources, and other objects. Manual changes to managed objects appear as drift in the next plan and are reset to the state described in YAML when the configuration is applied. If a managed object is manually deleted, Weldall plans to recreate it. This only affects objects created or imported through IaC. Everything else remains untouched.

## Start a workspace

<Steps>
1. **Prepare a machine client**

Use the Weldall CLI to run IaC commands. It authenticates with a machine client that was created in Weldall and granted the `weldall:iac` scope. Give the CLI its client ID and key through environment variables:

```sh
export WELDALL_M2M_CLIENT_ID=platform-ci
export WELDALL_M2M_KID=ci-2026
export WELDALL_M2M_PRIVATE_JWK='<private P-256 JWK JSON>'
export WELDALL_M2M_PUBLIC_JWK='<public P-256 JWK JSON>'
```

These variables also decide what help shows: the IaC commands appear in `weldall --help` only while they are set, because a browser login never makes them usable.

<Aside type="caution" title="Protect the private key">
  Never put the private key in the YAML configuration or commit it to Git.
</Aside>

2. **Initialize the workspace**

   ```sh
   mkdir platform-access && cd platform-access
   weldall init --name platform-access --issuer https://weldall.example.com
   ```

   This creates `weldall.yml`, `weldall.lock.yml`, and a `weldall/` directory. Commit the manifest and lockfile together.

   </Steps>

### Split the workspace into fragments

A workspace might look like this:

<FileTree>
  - platform-access/ - **weldall.yml** Root manifest - weldall.lock.yml Versioned server state and
  object mappings - weldall/ - access.yml Scopes and assignments - runtime.yml Resources and machine
  clients - imports/ Optional, used by `weldall import` - emailAssignment-alice.yml Generated import
  fragment
</FileTree>

The root manifest generated by `init` contains the workspace metadata and includes every YAML file below `weldall/`:

```yaml
# weldall.yml
apiVersion: weldall.dev/v1
workspace:
  name: platform-access
  issuer: https://weldall.example.com
include:
  - weldall/**/*.yml
```

The included files are fragments. They do not repeat `apiVersion` or `workspace`; they contain only one or more object sections such as `scopes`, `resources`, or `emailAssignments`. The CLI merges all fragments into one complete configuration. Your team can organize the files by application, ownership, environment, or any other structure that works for you.

## Declare access

```yaml
# weldall/access.yml
scopes:
  expenses_read:
    key: expenses:read
    description: Read expenses

emailAssignments:
  alice:
    email: alice@example.com
    scopes:
      - expenses:read

groupAssignments:
  finance:
    provider: company-directory
    groupId: finance-team
    scopes:
      - expenses:read
```

`scope.expenses_read`, `emailAssignment.alice`, and `groupAssignment.finance` are names that IaC uses only inside this workspace. The part after the dot comes from the corresponding YAML map key. These IaC-only names do not change the actual objects in Weldall: A scope is still identified there by values such as `expenses:read`, and a person by an email address such as `alice@example.com`.

The group provider must already exist or be declared in the same workspace. Disabled drafts may be referenced but grant no permissions. The CLI does not check whether the specified group ID actually exists.

Resources and machine clients use the same file format:

```yaml
# weldall/runtime.yml
resources:
  expenses:
    key: expenses
    name: Expenses API
    resourceIdentifier: https://expenses.example.com/api
    authorizationServer: https://expenses.example.com
    downstreamClientId: expenses-api
    enabled: true
    skillDiscoveryEnabled: false
    requestPrefixes:
      - https://expenses.example.com/api
    scopes:
      - expenses:read

machines:
  reporter:
    clientId: expense-reporter
    name: Expense reporter
    enabled: true
    publicKeys:
      ci-2026:
        kty: EC
        crv: P-256
        x: IOqiZZjB6aPt6WuPSZw_sJxwdEueJ3AFo-AkI-c_sx0
        y: 8oDde4-gGqCC4jGY_vwNBbaAw8l4Xti8cv6NRtoinjk
    resources:
      - expenses
    scopes:
      - expenses:read
```

Only public machine keys belong in the manifest.

Managed connectors can also be declared in YAML. The manifest carries only public policy; OAuth client secrets are entered in the administration UI and are never accepted by the CLI. `envelopeProvider` is immutable after creation. Google connectors list exact Google OAuth scopes. Atlassian Cloud connectors must use resource-level grants, at least one allowed Jira or Confluence product scope, and at least one allowed site `cloudId`.

```yaml
connectors:
  google:
    key: google
    name: Google Workspace
    type: google
    enabled: false
    envelopeProvider: LOCAL_ENV
    requiredScopes: []
    provider:
      clientId: google-client-id.apps.googleusercontent.com
      allowedScopes:
        - https://www.googleapis.com/auth/calendar.readonly
      defaultScopes:
        - https://www.googleapis.com/auth/calendar.readonly
  company_jira:
    key: company-jira
    name: Company Jira
    type: atlassian
    enabled: false
    envelopeProvider: OPENBAO
    requiredScopes:
      - jira:use
    provider:
      clientId: atlassian-client-id
      grantType: resource
      products:
        - jira
      allowedCloudIds:
        - 8594f221-9797-5f78-1fa4-485e198d7cd0
      allowedScopes:
        - read:jira-work
        - read:jira-user
      defaultScopes:
        - read:jira-work
```

Connector manifests can be planned and applied like any other object. Manual UI edits to managed connector policy appear as drift, while provider secrets remain outside the manifest.

The CLI welcome page logo can be managed as a singleton setting. An empty URL removes the company logo:

```yaml
cli:
  logoUrl: https://example.com/brand-logo.svg
```

Administrator-managed skills use inline Markdown and explicitly declare every configurable field:

```yaml
skills:
  review_expenses:
    slug: expenses.review
    title: Review expenses
    content: |
      # Review expenses

      Check each expense against the policy.
    requiredScopes:
      - expenses:read
    visibility: HIDDEN_IF_UNALLOWED
    meta:
      tags:
        - finance
        - review
      owner: Finance Operations
      appearance:
        icon: file-text
        gradientFrom: "#555BD6"
        gradientTo: "#7773E5"
        darkGradientFrom: "#2A2660"
        darkGradientTo: "#403A86"
    lastUpdatedAt: "2026-08-20"
```

`meta.appearance.icon` accepts canonical kebab-case names from the [Lucide icon catalog](https://lucide.dev/icons/). Gradient overrides are applied only when both colors in a light or dark pair are six-digit hex colors; otherwise Weldall uses the deterministic slug-based fallback.

The slug is the skill identity, so changing it replaces the skill. An IaC-managed skill remains editable in the admin UI; such edits are drift and the next apply restores the YAML state. Administrator-managed skills may override resource-published skills with the same canonical ID. Discovered skills and catalogs cannot be imported or managed.

## Public configuration, UI-only credentials

`sharedConnections`, `groupProviders`, and `loginProviders` use disabled drafts without placeholder secrets. Create with `enabled: false`, apply, provision credentials in the admin UI, then explicitly enable in YAML and apply again. Provisioning/rotation never enables a disabled object; disabling preserves its credential.

```yaml
connectors:
  atlassian_mcp:
    key: atlassian-mcp
    name: Atlassian MCP
    type: atlassian-mcp
    enabled: false
    envelopeProvider: LOCAL_ENV
    requiredScopes: []
    provider:
      allowedScopes: [read:jira:agent-interface]
      defaultScopes: []

sharedConnections:
  bot:
    key: atlassian-bot
    connectorKey: atlassian-mcp
    name: Team bot
    enabled: false
    useScopes: [jira:use]
    credentialManagerEmail: alice@example.com
    serviceAccountLabel: Team service account
    provider:
      kind: service-account-api-key
      cloudIds: []

groupProviders:
  directory:
    key: company-directory
    name: Company directory
    adapterType: management-api-v1
    baseUrl: https://directory.example.com
    enabled: false

loginProviders:
  sso:
    id: 61726b4a-d245-49c5-adb7-80481fd68b13
    name: Company SSO
    buttonLabel: Continue with SSO
    buttonColor: "#2563eb"
    issuer: https://idp.example.com
    clientId: weldall
    tokenEndpointAuthMethod: client_secret_post
    enabled: false
```

The example assumes that `jira:use` exists (or is declared in the same workspace) and Alice is an existing Weldall user. The credential manager receives no additional invocation rights. Only scoped service-account connections can be managed; personal OAuth connections cannot be imported. Both connector and connection must be enabled for use. Disabled group providers grant no group permissions, and disabled login providers cannot start a login.

A plan checks credential presence and known prerequisites, not upstream token validity. Public planning/import does not decrypt credentials or contact OpenBao. Activation and credential operations retain provider-specific validation and fail closed. Issuer is immutable; changing a credential-bound client ID or directory endpoint requires explicit UI reprovisioning rather than silently reusing a credential at a new authority.

### Identity administration and approval

`weldall:iac` is a privileged configuration-administrator scope: it can change public login/group identity policy, but cannot read or provision secrets. Login activation and authority changes to an active login provider require a plan-specific acknowledgement:

```sh
weldall plan --json
# Review actions marked requiresAuthorityConfirmation, then copy this plan's digest:
weldall up --yes --acknowledge-authority <digest>
```

`--yes` alone is insufficient. A changed plan needs a new acknowledgement; the server enforces this for API callers too. IaC cannot disable/delete the last active login provider or reset the installation. The existing confirmed UI recovery path remains separate.

### Import, drift, and recovery

```sh
weldall import connector company-jira --as connector.company_jira
weldall import sharedConnection atlassian-bot --as sharedConnection.bot
weldall import groupProvider company-directory --as groupProvider.directory
weldall import loginProvider <existing-provider-uuid> --as loginProvider.sso
```

Import keeps identity, callback URL, activation, credential manager, and encrypted credentials unchanged. It writes public configuration and bindings only; the next plan is a no-op. State move and unmanage also preserve credentials. Public UI changes appear as drift; secret rotation does not, although it can invalidate an older plan.

If a credential-bearing object is manually deleted, restore it disabled, provision its credential again, and explicitly enable it. IaC does not recover deleted secrets. Deleting a connector/group provider is blocked while unmanaged or foreign-workspace dependencies remain. Deletion in Weldall does not revoke upstream tokens.

### Rollout and compatibility

Pending login attempts started before this upgrade must be restarted. Attempts are now bound to the provider's creation timestamp as well as its version, so deleting and recreating the same provider UUID cannot revive an old callback. Existing sessions are not revoked by this check.

Deploy database migrations and the matching server first, regenerate the Prisma client/restart the server, then upgrade the CLI. The new contracts require discovery feature `iac-ui-secrets-v1`. Legacy workflows still work against older servers; new sections/imports fail before mutation when unsupported. An omitted new section is not an explicit empty section: servers reject incompatible partial snapshots of workspaces already managing those kinds rather than deleting unknown objects. To remove the last object in such a section, retain the explicit empty map, for example `groupProviders: {}`.

Credentials and encryption formats are retained by migration. Running an old server binary against the migrated schema is not supported; rollback requires a compatible database backup, not just downgrading the CLI.

## Essential CLI commands

| Command                                            | Purpose                                                                                           |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `weldall init --name … --issuer …`                 | Creates a workspace with a root manifest, lockfile, and fragment directory.                       |
| `weldall validate`                                 | Reads and validates the root manifest and all fragments locally without contacting the server.    |
| `weldall plan`                                     | Compares the YAML configuration with the current server state without changing anything.          |
| `weldall up`                                       | Shows a fresh plan, asks for confirmation, and then applies it.                                   |
| `weldall up --yes`                                 | Applies without the general prompt; login authority changes still require plan-specific approval. |
| `weldall import <kind> <identity> --as <iac-name>` | Claims an existing object and gives it a name for this IaC workspace.                             |
| `weldall unmanage <iac-name> --yes`                | Stops managing an object without deleting the object itself.                                      |
| `weldall state mv <old> <new>`                     | Changes the name IaC uses to manage the object; the Weldall object remains unchanged.             |
| `weldall state pull`                               | Rebuilds the lockfile mappings from the server state.                                             |

`weldall plan --json` prints the plan as machine-readable JSON. With `weldall plan --detailed-exit-code`, exit code `2` signals that changes are pending.

## Import an existing object

A matching manual object is never claimed automatically. Import it explicitly:

```sh
weldall import emailAssignment alice@example.com --as emailAssignment.alice
weldall import scope expenses:read --as scope.expenses_read
weldall import skill expenses.review --as skill.review_expenses
```

Import preserves the object, writes its current configuration to `weldall/imports/`, and updates the lockfile.

Removing a managed declaration makes the next apply delete that object. To keep the object but stop managing it, remove the declaration and run:

```sh
weldall unmanage scope.expenses_read --yes
```

You can change the name used only inside IaC without renaming or recreating the actual Weldall object. For example, this command renames `scope.expenses_read` to `scope.expenses_view` inside IaC; the `expenses:read` scope in Weldall remains the same:

```sh
weldall state mv scope.expenses_read scope.expenses_view
```

You can also recover the lockfile from the server state:

```sh
weldall state pull
```

The complete field reference is the [manifest JSON Schema](https://github.com/seibert-external/weldall/blob/main/schemas/weldall-manifest-v1.schema.json).

Weldall unterstützt OAuth 2.0 Client Credentials für Backend-Workloads. Eine Workload authentisiert sich mit RFC 7523 `private_key_jwt` als eigene Identität; sie meldet keinen Menschen an und verwendet nicht den öffentlichen Client `weldall-cli`. Weldall liefert ein fünf Minuten gültiges JWT für genau eine ausgewählte Ressource und ausschließlich ausgewählte Scopes, die diese Ressource unterstützt.

## Expenses A registrieren

1. Scopes anlegen und Expenses B unter **Resources** registrieren.
2. Ein ES256-P-256-Schlüsselpaar im Secret-System der Workload erzeugen. Der private JWK bleibt dort.
3. Unter **Workload clients** `expenses-a`, den öffentlichen JWK und eine eindeutige `kid` registrieren.
4. Unter **Workload access** Expenses B bei **Resources** und die benötigten Einträge bei **Scopes** auswählen.

Ressourcen und Scopes werden unabhängig ausgewählt. Die Registrierung einer Workload, Ressource oder eines unterstützten Scopes vergibt noch keine Berechtigung; eine Token-Anfrage benötigt eine ausgewählte Ressource, ausgewählte Scopes und die Unterstützung aller angeforderten Scopes durch diese Ressource. Weldall lehnt private JWKs ab und unterstützt weder Client Secrets noch entfernte Client-JWKS-URLs.

## Token anfordern

Das SDK erzeugt die kurzlebige Assertion und den passenden DPoP-Nachweis:

```ts
import { requestWorkloadToken } from "@weldall/sdk";

const token = await requestWorkloadToken({
  issuer: "https://weldall.example.com",
  clientId: "expenses-a",
  resource: "https://expenses-b.example.com/api",
  scopes: ["expenses-b:read"],
  kid: process.env.WORKLOAD_KEY_ID!,
  key: loadKeyFromSecretStore(),
});
```

Private Schlüssel müssen aus Secret Store, KMS oder einer Plattform-Credential-Lösung kommen. Sie gehören nie in Weldall, Manifeste, Quellcode oder Logs. Die Antwort enthält kein Refresh Token.

## Expenses B schützen

```ts
import { inMemory } from "@weldall/sdk";
import { initWorkloadAuth, type WorkloadVariables } from "@weldall/sdk/hono";
import { Hono } from "hono";

const workloads = initWorkloadAuth("https://weldall.example.com", {
  resource: "https://expenses-b.example.com/api",
  publicOrigin: "https://expenses-b.example.com",
  supportedScopes: ["expenses-b:read"],
  allowedClientIds: ["expenses-a"],
  replayStore: inMemory(), // im Cluster einen gemeinsamen atomaren Store verwenden
});

const app = new Hono<{ Variables: WorkloadVariables }>();
app.get("/api/expenses", workloads.protectWorkload({ scopes: ["expenses-b:read"] }), (context) =>
  context.json({ caller: workloads.getWorkloadAuth(context).clientId }),
);
```

Für jeden API-Aufruf wird ein frischer DPoP-Proof mit Workload-Schlüssel und Access-Token-Hash erzeugt. Der Verifier prüft Weldall-Issuer und fest gebundene JWKS, die einzelne exakte Audience, Ablauf, `workload:<client_id>`-Subject, Workload-Tokenmarker, lokale Client-Allowlist, Scopes, Schlüsselbindung, HTTP-Methode/URL/Token-Hash und Proof-Replay.

Workload-Tokens verwenden `typ=weldall-workload+jwt` sowie die signierten Claims `identity_type=workload` und `token_type=workload`. Sie enthalten keine Benutzer-E-Mail und werden nicht mit Benutzertokens verwechselt. Client Credentials erlauben keine Benutzer-Impersonation.

## Rotation und Widerruf

Zuerst den neuen öffentlichen Schlüssel registrieren, dann den privaten Schlüssel ausrollen, während einer Übergangszeit beide Schlüssel akzeptieren und schließlich den alten Schlüssel widerrufen. Registrierte Schlüssel sind sofort aktiv und bleiben bis zum Widerruf gültig. Alternativ können Clients deaktiviert oder ihre Workload-Zugriffsauswahl entfernt werden. Das stoppt neue Token-Ausstellung sofort; bereits ausgestellte Tokens laufen spätestens nach fünf Minuten ab.

Lifecycle-, Ausstellungs- und Ablehnungsereignisse erscheinen unter **Audit logs**, ohne Assertions, Tokens, Proofs, private Daten oder JWK-Koordinaten.

## Sicherheitsgrenzen und spätere Flows

Entfernte Workload-JWKS-URLs werden absichtlich nicht unterstützt; damit entfällt ein SSRF-Pfad über Client-Metadaten. Horizontal skalierte Zielservices benötigen einen gemeinsamen atomaren `ReplayStore`; `inMemory()` ist nur für Entwicklung und einen einzelnen Prozess geeignet.

Im MVP stellt Weldall Workload-Access-Tokens direkt aus. Der interaktive Benutzerflow bleibt über ID-JAG und ressourcenlokale Tokens gebrokert. Workload-Föderation, Self-Service-Registrierung, gebrokerte Workload-Assertions und expliziter delegierter Benutzeraustausch nach RFC 8693 sind kompatible spätere Erweiterungen, aber kein Bestandteil von Client Credentials.
